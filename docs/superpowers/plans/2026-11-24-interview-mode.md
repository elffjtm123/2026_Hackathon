# 면접 연습 기능 개발 계획 (초안)

- 작성일: 2026-11-24
- 근거: 12주차 주간학습보고서(2026.11.16~11.22)의 "4. 면접 기능 모델·구성 조사", "5. 답변 평가 기준 조사", "내주 계획"
- 상태: 결정 사항 확정(2026-11-24, §7). 설계 문서: [`docs/superpowers/specs/2026-11-24-interview-mode-design.md`](../specs/2026-11-24-interview-mode-design.md)
- 실행 환경: 로컬 AI 모드 전용. 배포하지 않으며, 배포하더라도 사용자가 내려받아 로컬에서 실행한다.

## 1. 목표와 범위

보고서의 내주 계획 다섯 가지를 그대로 이번 개발 범위로 삼는다.

1. 서류 업로드와 추출 내용 확인·수정 (초기 버전)
2. Qwen3.5-9B Q4_K_M으로 공통 질문과 서류 기반 예상 질문 생성
3. 질문과 답변을 연결해 기록하고, 종료 화면에서 질문별 결과와 전체 종합 피드백을 나눠 표시
4. 질문 유형별 평가 기준과 답변 수준 예시를 작성하고, 답변 근거를 함께 반환하는 평가 형식
5. 질문 품질(관련성·중복·사실 왜곡)과 자동 채점(반복 안정성·사람 평가 일치도) 검증 실험 준비

질문은 세 종류로 구성한다(§4): **공통 질문**(기본·인성), **서류 기반 질문**(직무·경험), **답변 기반 추가 질문**. 추가 질문은 질문 구조와 데이터 형식을 이번에 함께 설계하되, 구현은 공통·서류 기반 질문이 동작한 뒤 마지막 단계로 진행한다.

**범위 밖**: 답변 도중 바로 이어지는 실시간 추가 질문(§4.3의 1차 방식으로 대체), 이미지 기반(스캔) PDF OCR, 시선·맥박·목소리 활성도를 내용 점수에 합산하는 것.

진행 흐름:

```
서류 입력 → 추출 내용 확인·수정 → 직무 입력 → 질문 생성·선택
  → [생성 모델 정리] → 1라운드 면접(본 질문) → [실시간 모델 정리]
  → 추가 질문 생성 → [생성 모델 정리] → 2라운드 면접(추가 질문) → [실시간 모델 정리]
  → 답변 평가(자동 시작) → 결과 화면
```

생성 모델과 실시간 모델(ASR·시선·맥박)이 동시에 메모리에 올라가지 않게 하는 것이 핵심 제약이다. 1·2라운드는 한 세션 안에서 진행하고, 라운드 사이에는 "대기" 상태를 둔다. 추가 질문을 쓰지 않으면 2라운드 부분을 건너뛴다.

## 3. 단계별 작업

각 단계는 독립적으로 동작을 확인할 수 있게 나눴다. 구현은 전역 지침의 Tier 3(coder + reviewer, 스키마·프로토콜 변경 포함)으로 진행하고, coder 브리프에 `tdd`, reviewer 브리프에 `code-review`를 넣는다.

### 단계 1. 서류 입력과 추출 확인

- 백엔드: `POST /api/v1/interview/documents` — PDF·DOCX·TXT 업로드, 텍스트 추출 결과 반환
  - 추출기는 인터페이스(`DocumentExtractor`) 뒤에 두고, pypdf(PDF)·python-docx(DOCX)·그대로 읽기(TXT)로 시작한다. 샘플 서류로 확인해 표·다단 레이아웃 추출이 부족하면 Docling 구현을 추가한다.
  - 파일 크기·페이지 수·글자 수 상한, 확장자와 실제 형식 확인. 원본 파일은 저장하지 않는다.
  - 추출 텍스트는 질문 생성이 끝나면 버린다. 세션에는 질문별 근거 문장만 남는다.
  - 로컬 AI 모드가 아니면 면접 API를 거부하고 안내한다(요약 API와 같은 조건).
  - 추출 실패(스캔 PDF 등)는 "텍스트를 찾지 못함"으로 알리고 직접 붙여넣기를 안내한다.
- 프론트: 면접 준비 화면에 서류 종류(자기소개서·이력서·포트폴리오)별 업로드, 추출 결과 편집 영역, 지원 직무 입력
- 완료 기준: 샘플 PDF·DOCX·TXT 각각에서 추출 → 편집 → 다음 단계로 넘어가는 흐름이 동작. 빈 문서·초과 크기·잘못된 형식 테스트 통과

**샘플 서류 준비** (단계 1과 함께 진행)

- 준비된 포트폴리오가 없으므로 먼저 인터넷에서 쓸 수 있는 샘플을 찾는다. 조건은 실제 개인의 정보가 아닐 것, 재사용이 허용된 자료일 것(공공 양식·예시, 공개 라이선스)이다. 실제 사람의 공개 포트폴리오는 개인정보라서 쓰지 않는다.
- 조건에 맞는 자료가 없으면 가상 인물로 직접 만든다. 공공 표준 이력서·자기소개서 양식의 구성을 참고한다.
- 구성(제안): 3세트 — AI 엔지니어 신입(프로젝트 경험 많음), 백엔드 개발자 신입(인턴 경험), 비개발 직무(기획·마케팅, 활동 위주). 세트마다 이력서·자기소개서·포트폴리오를 PDF·DOCX·TXT로 나눠 형식별 추출도 함께 확인한다.
- 질문 생성 검증용으로 일부러 짧은 서류, 금지 주제(가족·출신 지역 등)가 들어간 서류도 하나씩 만든다.
- 저장 위치: `tests/fixtures/interview/` (가상 자료라 저장소에 둘 수 있음)

### 단계 2. 공통 질문과 서류 기반 질문 생성

- `LocalScriptSummarizer`의 llama-server 실행·정리 부분을 공통 실행기로 분리하고, 그 위에 질문 생성기를 만든다. 요약 기능 동작은 그대로 유지한다(회귀 테스트를 먼저 고정).
- `ModelExecution`에 면접 전 질문 생성용 소유자를 추가하거나 `reserve_summary`를 일반화한다. 다른 세션이 진행 중이면 거부한다. 라운드 사이 추가 질문 생성과 면접 후 평가는 단계 3·6의 세션 소유 방식을 따른다.
- 질문 구성 방식은 §4.1, §4.2를 따른다.
- 면접 구성(유형별 질문 수, 추가 질문 최대 수, 순서)은 코드에 박지 않고 "면접 구성" 설정 하나로 둔다. 첫 버전은 기본 구성(§4.2) 하나만 쓰고, 구성을 바꾸는 화면은 나중에 만든다.
- 공통 질문은 목록에서 §4.1의 고르기 규칙으로 뽑는다.
- 사용자는 생성된 질문을 고르거나 지우고 순서를 바꾼 뒤 면접을 시작한다.
- 완료 기준: 생성 → 모델 정리 확인 → 실시간 세션 시작이 메모리 충돌 없이 이어짐. 근거 문장 검증, 중복 제거, 금지 주제 필터 테스트 통과

### 단계 3. 질문별 답변 기록

- 실시간 프로토콜(`app/realtime/events.py`, `src/lib/realtimeProtocol.ts`)에 면접용 이벤트 추가: 세션 시작 시 질문 목록, 진행 중 `question_started` / `question_ended` (질문 ID, 시각)
- 집계기(`aggregator.py`)가 받아쓰기 결과를 질문 구간별로 나눠 쌓는다. 질문 경계에 걸친 발화 처리 규칙을 정하고 테스트로 고정한다.
- **질문 표시**: 음성 없이 화면 텍스트로만 보여 준다.
  - 읽는 시간 = `3초 + 글자 수 ÷ 7초`, 최대 15초.
  - 읽는 시간이 끝나거나 사용자가 말을 시작하면(둘 중 먼저 오는 시점) 질문을 화면에서 지운다. 질문을 보면서 답하면 실제 면접보다 쉬워지기 때문이다. 지운 뒤에는 남은 답변 시간과 남은 질문 수만 보여 준다.
  - **질문 다시 보기 버튼**: 질문마다 한 번 누를 수 있다. 누르면 읽는 시간만큼 질문을 다시 보여 주고, 그동안 답변 시간은 멈춘다. 사용 여부는 기록하지만 점수에는 반영하지 않는다.
- **진행 주도권은 면접관(시스템)에 있다.** 사용자가 질문을 넘기지 않고, 시스템이 답변이 끝났다고 판단하면 자동으로 다음 질문으로 넘어간다.
  - 답변 종료 판단: 발화가 있은 뒤 침묵이 4초 이어지면 답변이 끝난 것으로 본다. 생각하느라 멈추는 짧은 침묵에 넘어가지 않도록, 답변 시작 후 10초가 지나기 전에는 넘기지 않는다.
  - 제한 시간: 질문당 최대 답변 시간(2분, 자기소개는 1분 30초)이 지나면 현재 발화가 끝나는 대로 넘긴다.
  - 무응답: 읽는 시간이 끝난 뒤 15초 동안 발화가 없으면 무응답으로 기록하고 넘긴다.
  - 위 기준값은 모두 설정값으로 두고, 단계 7 데모 실험으로 조정한다.
  - 넘기기 전 처리: 그 질문 구간에서 시작한 발화의 최종 받아쓰기가 모두 도착할 때까지(최대 3초) 기다린 뒤 다음 질문을 띄운다. 발화는 시작 시각(`start_ms`)이 속한 질문에 붙이므로, 경계에 걸친 발화가 다음 질문으로 넘어가지 않는다.
  - 침묵 판단과 넘김은 서버가 한다. 발화 분리는 서버의 `SpeechSegmenter`가 하고, 20ms 프레임마다 유성 여부를 관찰할 수 있다. 판단 로직은 순수 모듈 `InterviewConductor`에 둔다(설계 문서 §4.1).
  - 넘어갈 때 "다음 질문입니다" 같은 짧은 전환 표시를 보여 준다. 사용자가 할 수 있는 조작은 질문 다시 보기와 면접 중단뿐이다.
- 기존 시선·음성 실시간 피드백은 그대로 둔다.
- **세션 구조**: 면접 하나를 세션 하나로 유지한다. 1라운드가 끝나면 세션을 "대기" 상태로 두고 실시간 모델만 내린 뒤, 추가 질문 생성이 끝나면 다시 올려 2라운드를 진행한다. 이를 위해 `ModelExecution`이 세션 소유권을 유지한 채 생성 모델을 잠깐 쓸 수 있게 바꾼다(라운드 사이 추가 질문 생성, 면접 후 평가).
- **저장**(설계 중 변경): 지금 화면은 로그인 없는 로컬 데모 경로를 쓰고 이 경로는 세션을 DB에 저장하지 않으므로, DB 테이블은 만들지 않는다.
  - 면접 진행·평가 중에는 서버 메모리(`InterviewStore`)에 질문 항목별 기록을 둔다. 항목: §4.4의 질문 데이터(공통 질문은 목록 ID 포함), 답변 받아쓰기, 질문별 시각, 넘어간 이유, 질문 다시 보기 사용 여부, 평가 결과.
  - 최종 결과와 받은 공통 질문 ID는 브라우저(localStorage)에 저장한다. "최근 3번 면접에서 받은 질문 제외"는 브라우저 기록으로 계산해 질문 생성 요청에 담아 보낸다.
  - 브라우저를 바꾸면 기록이 없고, 서버를 재시작하면 진행 중인 면접 기록이 사라진다.
- 완료 기준: 3개 질문 세션에서 각 질문에 해당 구간의 받아쓰기만 붙음. 침묵·제한 시간·무응답 세 경우 모두 자동으로 넘어가고, 무응답 질문은 빈 답변으로 기록. 질문 경계에 걸친 발화가 다음 질문에 붙지 않음. 읽는 시간 종료·발화 시작 시 질문이 지워지고, 다시 보기는 질문당 한 번만 동작하며 그동안 답변 시간이 멈춤

### 단계 4. 답변 평가와 종합 피드백

- 면접이 끝나면 평가를 자동으로 시작한다. 실시간 모델이 정리된 것을 확인하고 평가 모델을 띄우며, 진행 표시와 취소를 지원한다. 평가가 끝나기 전에도 받아쓰기와 음성·시선 결과는 먼저 보여 준다.
- 평가 항목, 비중, 등급 기준은 §5를 따른다. 각 등급에 답변 수준 예시를 붙인 평가 기준표를 `app/modules/interview/rubric.py`(가칭)에 데이터로 둔다.
- 호출 방식: 질문당 한 번 호출하고, 응답 안에 항목별 칸을 따로 둔다. 항목마다 따로 호출하는 방식과는 단계 7(시간)·단계 8(일관성)에서 비교한다.
- 평가 형식: 항목별 `{grade, evidence_quote, evidence_source, reason, improvement}`. `evidence_quote`가 실제 답변 받아쓰기에 없으면 그 항목은 무효로 처리한다. `evidence_source`는 본 답변/추가 답변 구분이다.
- 추가 질문의 답변은 원래 질문과 묶어 하나로 평가한다.
- "평가 불가": 아래 경우 0점이 아니라 평가 불가로 처리하고, 평균에서 빼고, 결과 화면에 이유를 표시한다. 기준값은 데모 실험으로 조정한다.
  - 무응답
  - 답변이 너무 짧음: 받아쓰기 20음절 미만
  - 인식 실패: 발화 시간에 비해 받아쓰기 음절 수가 비정상적으로 적음
- 종합 피드백: 질문별 결과를 모아 강점·보완점·다음 연습 목표를 생성. 시선·맥박·목소리 활성도는 점수에 넣지 않고 별도 참고 영역으로만 보여 준다.
- 완료 기준: 평가 불가 처리, 비적용 항목 제외 환산, 근거 문장 검증 테스트 통과. 평가 실패 시에도 받아쓰기와 기존 음성·시선 결과는 볼 수 있음

### 단계 5. 결과 화면

- `InterviewContent.tsx`의 "질문별 결과" 자리표시자를 질문별 카드(질문 / 답변 받아쓰기 / 항목별 등급과 근거 / 보완점)로 바꾼다. 추가 질문은 부모 질문 카드 안에 이어서 표시한다.
- 상단에 전체 종합 피드백, 하단에 기존 `SessionSummary`·`SessionInsights`(음성·시선 참고 정보)를 둔다.
- 받아쓰기 기반 평가라 인식 오류가 점수에 영향을 줄 수 있음을 안내한다.
- 완료 기준: 브라우저에서 생성 → 면접 → 결과까지 한 번에 확인, 평가 불가·부분 결과 표시 확인

### 단계 6. 답변 기반 추가 질문

- §4.3의 2라운드 방식으로 구현한다. 1라운드 종료 → 세션 대기 상태 → 실시간 모델 정리 → 추가 질문 생성 → 생성 모델 정리 → 실시간 모델 재시작 → 2라운드 시작. 모두 같은 세션 안에서 진행한다(단계 3 세션 구조).
- 2라운드 전환 대기 시간은 단계 7 데모 실험에서 확인한다. 너무 길면 추가 질문을 "다음 연습용 질문"으로 결과 화면에만 보여 주는 방식으로 낮춘다.
- 완료 기준: 1라운드 답변에서 빠진 요소를 근거로 추가 질문이 생성되고, 2라운드 답변이 부모 질문 평가에 반영됨. 빈 답변에는 추가 질문을 만들지 않음

### 단계 7. 데모 파일로 전체 흐름 성능 확인

구현을 마친 뒤, 실제 사용 흐름에서 병목 없이 동작하는지 데모 파일로 반복 실험한다. 사람이 매번 면접을 보지 않아도 같은 조건으로 다시 돌릴 수 있게 만든다.

- 데모 파일
  - 샘플 서류 3세트(단계 1)
  - 답변 음성 파일: 질문별 가상 답변을 녹음하거나 생성해 둔다. 좋은 답변, 짧은 답변, 일반론 답변, 중간에 길게 멈추는 답변, 무응답을 섞는다.
  - 기존 실험 기록 기능(`app/realtime/experiment_recorder.py`, `stt-experiments`)으로 음성을 파이프라인에 재생할 수 있는지 먼저 확인하고, 안 되면 재생용 스크립트를 만든다.
- 측정 항목

  | 항목 | 확인 내용 |
  |---|---|
  | 질문 생성 시간 | 1·2차 호출 각각, 모델 로딩 포함 |
  | 라운드 전환 대기 | 실시간 모델 정리 → 추가 질문 생성 → 실시간 모델 재시작까지 |
  | 평가 시간 | 질문 8개 + 추가 질문 2개 기준. 항목별 호출과 질문당 1회 호출 비교 |
  | 메모리 최고치 | 각 단계에서 프로세스 메모리. 16GB 맥북 기준 |
  | 자동 넘김 정확도 | 멈춤이 있는 답변에서 너무 일찍 넘기는 비율, 답변이 끝났는데 늦게 넘기는 시간 |
  | 질문 구간 정확도 | 경계에 걸친 발화가 다른 질문에 붙는 비율 |

- 결과에 따라 바꿀 것: 평가 호출 방식, 2라운드 유지 여부, 침묵 시간·최소 답변 시간·무응답 시간·읽는 시간 기준값, 평가 불가 기준(20음절)
- 완료 기준: 데모 3세트를 끝까지 돌려 측정표를 채우고, 기준을 넘는 병목이 있으면 원인과 대응을 기록

### 단계 8. 품질 검증 실험 준비

- 질문 품질: 같은 서류 3~5세트로 각각 여러 번 생성, 관련성·중복·사실 왜곡·유형 오분류를 사람이 표시하는 기록 양식과 스크립트 준비
- 추가 질문 품질: 지적한 빠진 요소가 실제로 답변에 없는지, 답변 내용과 맞는지 표시
- 채점 안정성: 같은 답변을 N회(예: 5회) 평가해 항목 등급의 표준편차·일치율 측정
- 사람 평가 일치도: 답변 샘플 20개 내외를 사람 2명과 모델이 같은 기준표로 채점, 가중 카파 또는 순위 상관으로 비교
- 비교 후보: Kanana-2-3B-Instruct (같은 입력·같은 지표로 비교)
- 결과는 기존 `stt-experiments`처럼 실험 기록으로 남기고, 주간 보고서에는 수치를 검증 전 결과로 표시한다.

## 4. 질문 구성 계획

### 4.0 공통 규칙

모든 질문이 지켜야 할 형식이다. 생성된 질문은 서버에서 아래 규칙을 검사하고 어기면 버리거나 다시 생성한다. 질문 예시와 규칙의 출처는 조사 문서 [`docs/research/2026-11-24-interview-question-references.md`](../../research/2026-11-24-interview-question-references.md)에 정리했다.

- 한 질문에는 하나만 묻는다. "~와 ~에 대해 말씀해 주세요"처럼 두 가지를 묻지 않는다. 한 질문에는 역량 하나만 담는다.
- 예/아니오로 끝나는 질문은 쓰지 않는다.
- 경험형 질문은 "~했던 경험 중 **가장** ~했던 한 가지"처럼 최상급과 "하나"를 넣어 구체적인 사례 하나를 고르게 한다(OPM).
- 상황형 질문은 장면(역할·사건·제약)을 먼저 주고 "어떻게 하시겠습니까?" 한 문장으로 끝낸다. 정답이 뻔하지 않은 딜레마로 만들고, 직무 지식 없이도 답할 수 있게 쓴다(OPM, Google re:Work). 상황형은 장면 설명 때문에 길어질 수 있으므로 길이 제한을 200자로 둔다.
- 그 밖의 질문은 한 문장, 100자 이내.
- 질문마다 적용할 평가 항목(`rubric_items`)을 정해 둔다(§5). 평가 시 이 항목만 채점한다.
- 유도형("~하셨죠?")과 반박형("그건 틀린 것 같은데요") 질문은 만들지 않는다(OPM). 압박 면접은 기본값에서 쓰지 않는다.
- 금지 주제: 성장 과정·가족, 나이, 결혼, 출신 지역, 종교, 외모·신체 조건, 재산 등 직무와 관계없는 개인 정보. 서류에 이런 내용이 있어도 질문 근거로 쓰지 않는다.
  - 근거: 채용절차의 공정화에 관한 법률 제4조의3(원문 확인)은 직무와 관계없는 신체 조건, 출신 지역, 혼인 여부, 재산, 가족의 학력·직업·재산을 **서류로** 요구하는 것을 금지한다. 면접에서 묻는 것을 금지하는 근거는 2017년 공공부문 블라인드 채용 지침이며, 이 지침의 원문은 아직 확인하지 못했다. 남녀고용평등법 제7조, 고령자고용법 제4조의4도 함께 참고한다.
  - 국내 기업 조사(사람인 2015, 2차 자료)에서 21.7%가 가족·성장 과정을 묻는다고 답했다. 실제로 자주 나오더라도 연습용 질문에서는 뺀다.

### 4.1 공통 질문

서류와 관계없이 누구에게나 묻는 질문이다. LLM을 쓰지 않으므로 생성 모델이 실패해도 면접을 진행할 수 있다. 기본 질문과 인성 질문 두 묶음으로 나눈다.

**기본 질문**

| 분류 | 예시 | 적용 평가 항목 | 위치 |
|---|---|---|---|
| 자기소개 | 1분 동안 자기소개를 해 주세요. | 질문·직무 이해 | 항상 첫 질문 |
| 지원 동기 | 이 직무에 지원한 이유는 무엇인가요? | 질문·직무 이해 | 앞부분 |
| 강점·약점 | 지원하신 직무에서 본인의 강점이 가장 잘 드러났던 경험 하나를 말씀해 주세요. | 구체성, 결과와 학습 | 중간 |
| 입사 후 계획 | 입사 후 첫 1년 동안 이루고 싶은 목표는 무엇인가요? | 질문·직무 이해 | 뒷부분 |
| 마무리 | 저희에게 궁금한 점이 있으면 질문해 주세요. | 평가하지 않음 | 선택, 마지막 |

- 국내에서 자주 묻는 질문은 지원 동기, 직무에 대한 생각, 직무 관련 강점 순이었고, 첫 질문은 자기소개가 가장 많았다(사람인 2015 조사, 2차 자료, 최신 자료는 찾지 못함).
- 기본 질문은 구조화 정도가 가장 낮은 유형이라(NCS가 "기존 면접"의 예로 듦), "장점이 뭔가요?" 같은 일반형 대신 **직무에 묶은 형태**로 쓰고 강점 질문은 경험형으로 바꾼다.
- 마무리는 "하고 싶은 말"보다 지원자가 질문하는 시간을 기본으로 둔다(GitLab, OPM). 점수에 넣지 않는다.
- 약점·입사 후 포부 질문의 구체적 문장은 1차 자료에서 찾지 못했다. 자체 작성 문장으로 쓰고 그렇게 표시한다.

**인성 질문**

인성 질문은 서류 내용과 관계없이 실제 면접에서 자주 나오는 주제라 공통 질문으로 둔다. 과거 경험을 묻는 경험형과 가상 상황을 주는 상황형을 함께 쓴다.

| 형태 | 주제 | 예시 | 적용 평가 항목 |
|---|---|---|---|
| 경험형 | 협업, 갈등 조율, 실패와 극복, 책임감 | 팀 프로젝트에서 의견이 가장 크게 엇갈렸던 순간 하나를 말씀해 주세요. | 협업과 의사소통, 구체성, 결과와 학습 |
| 상황형 | 갈등, 우선순위, 윤리·원칙, 압박 상황 | 마감 이틀 전, 팀원 한 명이 맡은 기능이 아직 동작하지 않는다는 사실을 알게 됐습니다. 어떻게 하시겠습니까? | 질문·직무 이해, 문제 해결과 판단 근거, 협업과 의사소통 |

- 경험형 주제는 OPM이 구조화 면접에 적합하다고 한 역량(팀워크, 의사소통, 대인관계, 갈등 관리, 설득)과 우리 주제(협업, 갈등, 실패, 책임감)를 대응시켜 고른다. 실패 질문은 Amazon처럼 무엇을 배웠는지까지 묻는다.
- 상황형 장면은 신입·학생 대상이므로 팀 프로젝트, 동아리, 인턴 장면을 쓴다.
- NCS 직업기초능력 경험·상황면접 예시문항(조사 문서 부록 A)을 따른다.
  - 경험형 추가 질문 순서: 상황 및 문제 → **역할** → 행동(과정, 노력, 의도, 가장 어려웠던 점) → 결과(**아쉬웠던 점과 개선할 점**)
  - 상황형 추가 질문 순서: 핵심 과제 → 핵심 이해관계자 → 행동과 의도 → **예상 결과**
  - 경험형 주질문에는 경험 출처 예시를 괄호로 붙인다(예: "(수업 프로젝트, 동아리, 인턴, 아르바이트 등)"). 학생도 답할 사례를 고르기 쉽다.
  - 상황형 주질문은 역할·사건·제약을 담은 3~5문장으로 쓴다. NCS 예시는 회사 업무 장면이 많아 학생 대상으로는 팀 프로젝트·동아리 장면으로 바꾼다.
  - 인성 주제는 NCS 직업기초능력 중 대인관계, 문제해결, 의사소통, 자원관리, 자기개발, 직업윤리에서 고른다.

- 상황형 답변은 실제 경험이 아니므로 "구체성"과 "결과와 학습"은 적용하지 않는다. 대신 상황을 어떻게 이해했는지, 어떤 기준으로 판단했는지, 관련된 사람과 어떻게 조율할지를 본다.
- 상황형 질문은 `{직무}`를 넣을 수 있는 틀로 일부 작성해 직무에 맞는 상황을 준다(예: "{직무} 업무 중 상사의 지시가 원칙에 어긋난다고 느끼면?").
- 경험형과 상황형이 같은 주제(예: 갈등)로 겹치지 않게 고른다.
- 상황형 질문 형식의 학술 근거로 Latham et al. (1980) "The situational interview"를 둔다. 서지는 DOI로 확인했으나 본문은 읽지 않았으므로, 내용을 인용할 때는 원문을 먼저 읽는다.

**공통 사항**

- 질문 목록은 `app/modules/interview/question_bank.py`(가칭)에 데이터로 둔다. 질문을 많이 준비해 두고 아래 규칙으로 골라 쓴다.
  - 분류·주제마다 10개 이상 준비한다. 기본 질문 4개 분류(자기소개, 지원 동기, 강점·약점, 입사 후 계획)와 마무리, 인성 경험형 6개 주제, 인성 상황형 6개 주제.
  - 초안은 NCS 예시문항과 OPM 문형을 기준으로 작성하고 사용자 검토 후 확정한다. 질문마다 따른 문형의 출처와 자체 작성 여부를 표시한다.
  - 한 면접에서 경험형과 상황형은 서로 다른 주제에서 고른다.
  - 최근 3번의 면접에서 받은 질문은 고르지 않는다(브라우저에 저장한 기록 기준). 남은 질문이 없으면 가장 오래전에 받은 것부터 다시 쓴다.
  - 직무가 입력되면 `{직무}` 자리를 채울 수 있는 질문의 비중을 높인다.
  - 상황형은 팀 프로젝트·동아리·인턴 장면으로 쓴다. 직무별 상황형 질문은 첫 버전에서 만들지 않는다.
- 직무 이름이 입력되면 `{직무}` 자리에 끼워 넣는다(LLM 없이 문자열 치환).
- "마무리"는 평가하지 않는 질문으로 표시하고 점수에서 뺀다.

### 4.2 서류 기반 질문 (직무·경험)

입력된 서류와 지원 직무로 LLM이 만드는 질문이다. 사실 왜곡을 줄이려고 한 번의 모델 로딩 안에서 두 번 호출한다.

**1차 호출: 서류에서 질문 재료 뽑기**

```json
{"items": [{"kind": "project | skill | activity",
            "quote": "서류 원문 그대로의 문장",
            "summary": "한 줄 요약"}]}
```

- `quote`가 추출 텍스트에 실제로 있는지 서버에서 확인하고 없으면 버린다.
- 금지 주제에 해당하는 재료는 이 단계에서 버린다.
- 사용자에게 재료 목록을 보여 주고 빼고 싶은 항목을 지울 수 있게 한다(선택 기능).

**2차 호출: 재료로 질문 만들기**

| 하위 유형 | 무엇을 묻나 | 재료 | 질문 형태 | 적용 평가 항목 |
|---|---|---|---|---|
| 직무 | 직무 지식, 기술 선택 이유, 직무 적용 방법 | skill, project + 지원 직무 | "서류에 쓴 X를 [직무]에서 어떻게 활용하겠나요?", "X 대신 Y를 고른 이유는?" | 질문·직무 이해, 문제 해결과 판단 근거 |
| 경험 | 서류에 적은 프로젝트·활동에서 맡은 역할, 실제 기여, 새로 배운 점 | project, activity | 행동 질문(STAR): "X 프로젝트에서 본인이 맡은 역할은?", "X 프로젝트를 하며 새로 배운 점은?" | 구체성, 문제 해결, 결과와 학습 |

**프로젝트 질문의 초점: 결과보다 역할·기여·배운 점**

프로젝트 질문의 목적은 결과가 좋았는지가 아니라, 지원자가 그 과정에서 어떤 일을 맡았고 실제로 기여했는지를 확인하는 것이다. 새로 배운 점을 묻는 질문이 특히 중요하다. 직접 일을 한 사람은 무엇을 왜 배웠는지 구체적으로 말할 수 있고, 그렇지 않은 사람은 일반론("협업의 중요성을 배웠다")에 머물기 쉽기 때문이다.

- 경험 질문은 아래 세 가지 중 하나를 중심으로 만든다. 결과 자체를 묻는 질문("결과가 어땠나요?")은 중심 질문으로 쓰지 않는다.
  - 역할: "그 프로젝트에서 본인이 맡은 역할과 직접 한 일은 무엇인가요?"
  - 기여: "본인이 없었다면 그 프로젝트에서 무엇이 달라졌을까요?", "본인이 내린 결정 중 가장 중요했던 것은?"
  - 배운 점: "그 프로젝트를 하며 새로 배운 기술이나 방식은 무엇이고, 왜 배워야 했나요?"
- 배운 점 질문은 배운 내용과 그것이 필요했던 계기(맡은 일에서 생긴 문제)를 함께 묻도록 만든다. 계기를 함께 들어야 실제 역할과 연결되는지 판단할 수 있다.
- 프로젝트 질문의 기본 흐름은 **참여자 구성 → 본인 역할 → 실제로 한 일 → 새로 배운 것**으로 고정한다(Amazon, OPM). 주질문이 이 중 하나를 묻고, 추가 질문이 빠진 단계를 묻는다.
- 서류 기반 질문의 목적은 서류에 쓴 주장을 확인하는 것이다(Google re:Work). 답변이 서류 내용과 어긋나면 그 부분을 다시 묻는다(GitLab).
- "왜 기술 X를 골랐나" 같은 기술 선택 질문은 1차 출처에 예시가 없다. 그래서 주질문보다는 판단 근거 추가 질문("어떤 대안을 고려했나요?", "그 선택의 단점은 무엇이었나요?")으로 쓴다(OPM, Google의 추가 질문 문형).

- 출력 형식: `questions[{subtype, text, material_index, intent, rubric_items[]}]`. `material_index`로 1차 재료와 연결해 근거 문장을 화면에 보여 준다.
- 인성 질문은 공통 질문(§4.1)에서 다룬다. 서류의 활동 재료에 협업 경험이 있으면 경험 질문의 적용 항목에 "협업과 의사소통"을 넣을 수 있다.
- 중복 제거: 같은 재료에서 나온 같은 하위 유형 질문은 하나만 남긴다. 그 밖에 문자 n-gram 유사도가 기준 이상인 질문 쌍도 하나만 남긴다(기준값은 실험으로 정함).
- 재료가 부족하면(예: 서류가 짧음) 공통 질문 비율을 늘리고, 화면에 "서류에서 질문 근거를 충분히 찾지 못함"을 알린다.

**기본 구성** (첫 버전 고정. 구성은 설정으로 두어 나중에 바꿀 수 있게 한다)

| 구성 | 개수 |
|---|---|
| 공통 - 기본 | 2 (자기소개 + 1개) |
| 공통 - 인성 | 2 (경험형 1 + 상황형 1) |
| 서류 - 직무 | 2 |
| 서류 - 경험 | 2 |
| 합계 | 8 (+ 추가 질문 최대 2) |

서류 재료가 부족하면 서류 기반 질문 수를 줄이고 공통 질문으로 채운다.

진행 순서: 자기소개 → 지원 동기 → 직무·경험 질문 → 인성 질문 → 입사 후 계획 → 마무리(지원자 질문, 평가하지 않음). 질문당 최대 2분이면 면접 전체는 20분 안팎이다.

### 4.3 답변 기반 추가 질문

본 질문 답변에서 평가 항목에 필요한 요소가 빠졌을 때 그 부분을 더 묻는 질문이다.

**무엇을 보고 만드나: 빠진 요소 종류**

| 빠진 요소 | 관련 평가 항목 | 질문 예 |
|---|---|---|
| 본인 역할 | 구체성 | "그중 본인이 직접 맡은 부분은 무엇이었나요?" |
| 판단 이유 | 문제 해결과 판단 근거 | "그 방법을 고른 이유는 무엇인가요?" |
| 결과 확인 방법 | 결과와 학습 | "그 결과는 어떻게 확인했나요?" |
| 배운 점 | 결과와 학습 | "그 경험 이후 달라진 점이 있나요?" |
| 협업 과정 | 협업과 의사소통 | "의견이 달랐던 팀원과는 어떻게 조율했나요?" |
| 구체적 사례 | 구체성 | "방금 말한 내용을 실제 사례 하나로 설명해 주세요." |

**빠진 요소를 찾는 신호**

추가 질문은 미리 정한 목록에서 고르는 방식을 기본으로 한다(OPM, Google은 추가 질문을 미리 준비하라고 함). LLM이 문장을 만들더라도 아래 신호와 빠진 요소의 대응을 제약으로 준다.

| 답변에서 보이는 신호 | 빠진 요소 | 판단 방법 | 근거 |
|---|---|---|---|
| "우리", "저희 팀"만 있고 "제가"가 없음 | 본인 역할 | 규칙(문자열)로 먼저 확인, LLM이 최종 판단 | OPM, Amazon |
| 구체적인 장면·숫자·시점이 없는 일반론 | 구체적 사례 | LLM | OPM, Amazon |
| STAR(상황·과제, 행동, 결과) 중 빠진 부분 | 해당 부분 | LLM | OPM |
| 결과는 있으나 배운 점이 없음 | 배운 점 ("다시 한다면 무엇을 다르게 하시겠어요?") | LLM | OPM |
| 상황형에서 행동을 하나만 말함 | 판단 이유 ("다른 방법도 있었을까요?") | LLM | OPM |

- LLM 출력 형식: `{gap_type, answer_quote, question}`. `gap_type`은 위 표의 값 중 하나로 제한하고, `answer_quote`는 추가 질문이 이어받는 답변 문장으로 실제 받아쓰기에 있어야 한다.
- 위 표의 질문 예는 LLM 생성이 실패하거나 검증에 걸릴 때 쓰는 고정 문장으로도 쓴다.
- 상황형 인성 질문에는 "결과 확인 방법"과 "배운 점"을 빠진 요소로 쓰지 않는다. 대신 NCS 상황면접 세부질문처럼 "이 상황의 핵심 과제는 무엇이라고 보나요?", "먼저 고려해야 할 사람은 누구인가요?", "그렇게 하면 어떤 결과가 나올 것으로 예상하나요?"를 묻는다. "비슷한 상황을 실제로 겪은 적이 있나요?"로 실제 경험을 묻는 것도 쓸 수 있다.
- 만들지 않는 경우: 답변이 비었거나 평가 불가인 질문, "마무리" 질문, 빠진 요소가 없는 답변.
- 프로젝트·활동 경험 질문의 추가 질문 우선순위: 본인 역할 → 배운 점 → 판단 이유 → 구체적 사례 → 협업 과정 → 결과 확인 방법. 배운 점이 일반론에 그치면("소통이 중요하다는 걸 배웠다") 빠진 것으로 보고 "그걸 배우게 된 구체적인 계기는 무엇이었나요?"로 묻는다. 결과 확인 방법은 다른 요소가 모두 있을 때만 묻는다.
- 개수 제한: 본 질문당 최대 1개, 면접 전체 최대 2개(설정 가능). 빠진 요소가 많은 답변부터 고른다.

**언제 묻나: 2라운드 방식 (1차 버전)**

현재 구조는 생성 모델과 실시간 모델이 동시에 올라가지 않으므로, 답변 직후 바로 묻지 않고 본 질문을 모두 끝낸 뒤 묻는다.

1. 1라운드: 본 질문 진행
2. 실시간 모델 정리 → 생성 모델로 추가 질문 생성 → 생성 모델 정리 (화면: "답변을 바탕으로 추가 질문을 준비하고 있습니다")
3. 2라운드: 추가 질문 진행. 화면에 어떤 본 질문에서 이어진 질문인지 표시

답변 직후 바로 묻는 방식은 두 모델을 동시에 올릴 때의 메모리 사용량을 측정한 뒤, 또는 작은 모델(Kanana-2-3B 등)로 추가 질문만 만드는 방식을 검토한 뒤 후속 과제로 판단한다.

**어떻게 평가하나**

- 추가 질문 답변은 부모 질문과 묶어 하나의 질문 단위로 평가한다. 추가 질문 답변에서 나온 근거도 부모 질문의 평가 항목 근거로 쓸 수 있다.
- 결과 화면에서는 각 근거가 본 답변에서 나왔는지 추가 답변에서 나왔는지 표시한다.

### 4.4 질문 데이터 형식

세 종류 질문을 한 형식으로 저장한다.

| 필드 | 설명 |
|---|---|
| `id` | 질문 ID |
| `kind` | `common` / `document` / `follow_up` |
| `subtype` | 공통: 분류 이름(인성은 `personality_behavioral` / `personality_situational`), 서류 기반: `job` / `experience`, 추가: `gap_type` |
| `text` | 질문 문장 |
| `intent` | 이 질문으로 확인하려는 것 (평가 시 프롬프트에 넣음) |
| `source_quote` | 서류 기반: 서류 근거 문장, 추가: 답변 근거 문장, 공통: 없음 |
| `rubric_items` | 적용할 평가 항목 목록. 빈 목록이면 평가하지 않음 |
| `parent_id` | 추가 질문일 때 부모 질문 ID |
| `order`, `round` | 진행 순서, 라운드(1 또는 2) |

## 5. 평가 항목과 비중

### 5.1 비중

5개 항목을 모두 같은 비중으로 둔다.

| 평가 항목 | 답변에서 확인할 내용 | 등급 | 5개 모두 적용 시 비중 |
|---|---|---|---|
| 질문·직무 이해 | 질문의 핵심과 직무·기술 개념을 적절하게 이해했는지 | 0~4 | 20% |
| 문제 해결과 판단 근거 | 문제와 제약, 대안 및 선택 이유를 설명했는지 | 0~4 | 20% |
| 경험·행동의 구체성 | 실제 사례와 본인의 역할·행동이 구체적인지 | 0~4 | 20% |
| 결과와 학습 | 배운 점과 그것을 배우게 된 계기를 본인 역할과 연결해 설명했는지, 결과를 어떻게 확인했는지 | 0~4 | 20% |
| 협업과 의사소통 | 타인의 의견을 반영하고 조율한 과정을 설명했는지 | 0~4 | 20% |

- 질문 점수: `20 × 등급 합계 ÷ (4 × 적용 항목 수)`. 적용 항목은 질문의 `rubric_items`(§4)로 정한다. 예: 직무 질문은 2개 항목이 각각 50%.
- 근거 인용이 답변에 없어 무효가 된 항목은 합계와 분모에서 모두 뺀다(구현 중 정한 잠정안, 사용자 확인 필요). 0점으로 세면 모델의 인용 실수가 사용자 점수를 깎기 때문이다. 대신 점수가 실제보다 높게 나올 수 있으므로, 이런 질문은 결과 화면에 "부분 평가"로 표시하고 빠진 항목을 보여 준다. 평가 호출은 검증 실패 시 1회 재시도한다.
- 전체 점수: 평가 가능한 질문 점수의 평균. 평가 불가 질문과 평가하지 않는 질문은 평균에서 뺀다.
- 이 항목 구성과 0~4등급은 기업 배점을 평균 낸 것이 아니라 자체 설계안이다.
- 평가 프롬프트는 항목마다 따로 채점하게 나눈다. 한 항목의 점수를 다른 항목의 근거로 쓰지 않게 해 후광 효과를 줄인다(OPM).
- 각 항목에 등급별 예시 답변(최소 1·3·4등급 수준)을 붙여 답변을 예시와 비교하게 한다(OPM은 질문별 행동 기준 예시 답변을 미리 만들라고 함). 채점 일관성이 실제로 좋아지는지는 단계 8에서 확인한다.
- 등급은 NCS 평가도구처럼 "기대행동이 답변에서 얼마나 관찰되었는가"로 정의한다(NCS 5단계: 완벽하게, 상당히, 약간, 거의 안 됨, 전혀 안 됨). 항목마다 낮은 수준(확인·인식), 중간(분석·공유), 높은 수준(종합·최적 선택·적용)의 기대행동을 적어 두고, 0~4등급을 이 관찰 정도에 대응시킨다.
- "결과와 학습"의 등급 기준은 배운 점에 무게를 둔다. 결과가 좋았다는 말만 있으면 높은 등급을 주지 않고, 본인 역할에서 생긴 문제와 그로부터 배운 구체적 내용이 있어야 3~4등급을 준다. 결과가 실패였거나 확인하지 못했어도 배운 점이 구체적이면 높은 등급이 가능하다.

### 5.2 같은 비중을 쓰는 이유

- Google과 GitLab 모두 항목별 배점을 공개하지 않는다.
- OPM 구조화 면접 FAQ는 비중을 다르게 줄 명확한 근거가 문서로 없으면 같은 비중이 가장 효과적이고 방어 가능하다고 권고한다. 다르게 줄 때는 이유를 기록하라고 한다. 또 한 면접에서 보통 4~6개 역량을 평가한다고 하며, 5개 항목은 이 범위 안이다.
- 연구 문헌(원문 확인 전, 서지만 기억에 의존): Dawes (1979) "The robust beauty of improper linear models", Bobko, Roth & Buster (2007) "The usefulness of unit weights in creating composite scores". 같은 비중이 추정한 가중치보다 새 데이터에서 크게 뒤지지 않는다고 보고한다. 우리는 가중치를 학습할 사람 채점 데이터가 아직 없다.
- 검증 실험(단계 8)에서 사람 채점 데이터가 쌓이면 비중 조정 여부를 다시 판단하고, 바꾸면 근거를 이 문서에 기록한다.

### 5.3 항목별 레퍼런스

| 항목 | 레퍼런스 | 연결 근거 |
|---|---|---|
| 질문·직무 이해 | Google re:Work 구조화 면접 가이드, OPM 구조화 면접 가이드 | 직무에 맞는 역량을 미리 정하고 모든 지원자를 같은 기준으로 평가. 질문과 추가 질문의 항목별 대응은 조사 문서 §5 표 참고 |
| 문제 해결과 판단 근거 | Google re:Work, OPM | 미리 정한 기준과 같은 척도로 답변 채점. 문제 해결이 OPM 역량 목록에 있는지는 원문 확인 필요 |
| 경험·행동의 구체성 | GitLab 면접 진행 지침, GitLab 디자이너 채용 페이지, GitLab 인프라 면접 페이지 | 과거 행동을 묻는 행동 질문, 답변은 구체적 사례여야 함, STAR 방식 안내 |
| 결과와 학습 | STAR의 Result 단계, GitLab 가치(Results for Customers, Iteration) | 결과 확인 방법과 배운 점 |
| 협업과 의사소통 | GitLab 가치(Collaboration), 모든 면접 단계의 가치 부합 항목 | 협업을 공식 평가 항목으로 둠 |

- 등급 기준(0~4): Google re:Work는 미리 정한 기준과 같은 척도로 채점하라고 하고, OPM 예시는 5단계 숙련도 척도에 최소 3개 수준의 설명을 붙이라고 한다. 각 등급에 답변 수준 예시를 붙인다.

## 8. 위험 요소

- 9B 모델 로딩·생성 시간: 질문 생성(2회 호출), 추가 질문 생성, 평가가 각각 수십 초 이상 걸릴 수 있음 → 진행 표시와 취소 지원, 타임아웃 설정
- 2라운드 전환 대기: 모델 정리·재로딩이 겹쳐 사용자가 오래 기다릴 수 있음 → 단계 7 데모 실험에서 측정
- 자동 넘김 오작동: 생각하느라 멈춘 것을 답변 종료로 보고 넘기거나, 답변이 끝났는데 늦게 넘길 수 있음 → 최소 답변 시간과 침묵 기준을 데모 실험으로 조정
- 질문을 지운 뒤 답하므로 질문을 잘못 기억하고 답할 수 있음 → 질문 다시 보기 버튼(질문당 1회)으로 보완
- `ModelExecution` 변경: 세션이 소유권을 유지한 채 생성 모델을 쓰게 바꾸면, 기존 요약 기능과 세션 시작·종료 동작이 깨질 수 있음 → 기존 모델 점유 테스트를 먼저 고정하고 변경
- 사실 왜곡·근거 없는 질문과 평가: 근거 문장 검증으로 걸러내지만 완전하지 않음 → 검증 실험에서 비율 측정
- 받아쓰기 오류가 점수와 추가 질문으로 전파됨 → 결과 화면에 안내, 평가 불가 기준 마련
- 요약 기능 회귀: 실행기 분리 시 기존 요약 테스트를 먼저 고정
